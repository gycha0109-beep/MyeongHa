# 승인 사주 결제·보관함 샌드박스 권한 검토안

이 변경은 기존 API 실행 역할이 승인 사주 주문과 보관함을 처리할 때 사용하는 함수만 연결합니다. 현재 저장소의 일반 구매 및 Records 호출은 기존 경로를 사용합니다.

- `commerce_approved_saju_sandbox_api_v1.sql`은 공개 스키마에 함수 여섯 개를 정의하고 모든 일반 실행 권한을 회수합니다. 주문 생성은 선택된 상품, 구매자의 명식 및 원본 재시도 범위를 다시 확인합니다. 결제 검증 조회는 승인 사주의 샌드박스 시도만 기존 서버 검증에 전달합니다.
- `commerce_approved_saju_sandbox_api_grant_v1.sql`은 위 함수 여섯 개와 보관함 조회 세 개에 한해 `myeongha_api_executor`에 실행 권한을 부여합니다. 비공개 스키마와 테이블 접근 권한은 별도로 부여할 필요가 없습니다.
- `commerce_approved_saju_sandbox_api_revoke_v1.sql`은 동일한 아홉 실행 권한을 회수합니다. 주문, 영수증, 보관함과 명식 데이터에는 변경이 없습니다.
- `commerce_approved_saju_legacy_archive_fence_v1.sql`을 승인 사주 풀이를 최초 저장하기 전에 적용합니다. 기본 보관함 목록과 상세 조회에서 승인 사주 풀이를 제외합니다. 승인된 보관함 옵션은 구매 권한이 유효한 풀이를 기존 목록에 포함하며, 상세를 열 때 권한을 다시 확인합니다. 권한을 회수한 뒤에도 이 SQL을 유지합니다.

## 승인 이후 적용 순서

1. 별도의 격리 배포 DB가 기준 스키마 및 복구 사본과 일치하는지 확인합니다. 코드에서 사용하는 샌드박스 채널과 로그인 경로를 확인합니다.
2. 구매 범위·권한·보관함·샌드박스 결제 후보와 API 함수 정의를 먼저 설치합니다. 격리 배포의 실행 역할, 함수 소유자 및 권한 목록을 확인합니다.
3. 위 아홉 실행 권한을 한 트랜잭션에서 부여합니다. 별도 테스트 호스트에 `createApprovedSajuSandboxHttpRuntimeV1`을 연결합니다. 기존 소유자 확인, 포트원 TEST 채널과 회원용 DB 연결을 사용하고, 영수증 쓰기에만 기존 내부 결제 역할의 별도 연결을 사용합니다. Cloudflare 보관함 옵션은 `MYEONGHA_APPROVED_SAJU_ARCHIVE=v1`입니다.
4. 회원과 다른 회원의 접근 범위, 샌드박스 주문 및 구매 후 발급 상태를 확인합니다. 샌드박스 결제 결과가 공식 Reading 권한으로 이어지는지 여부는 기존 영수증 정책으로 검사합니다.
5. 문제가 생기면 격리 배포에서 옵션을 먼저 끄고 권한 회수 SQL을 한 트랜잭션에서 실행합니다. 해당 역할로 신규 호출이 차단되고 기존 일반 경로가 유지되는지 확인합니다.

격리 PostgreSQL 17.6에서 실제 API 역할을 사용해 위 권한 부여와 회수를 테스트했습니다. 보관함 재열람에는 별도로 만든 합성 운영 형식 영수증을 사용했습니다. 이 검토안의 적용 대상은 샌드박스 결제와 보관함 연결까지입니다. 운영 결제·배포에는 공식 풀이 발급, 운영 DB 기준 일치와 복구 검증, PG 및 별도 운영 승인이 필요합니다.

테스트 화면은 `/reading.html?checkout=test`에서 서버가 소유자 권한을 확인한 뒤 표시됩니다. 격리 호스트는 기존 소유자 결제 콘솔의 포트원 SDK 경로와 브라우저 정책을 재사용합니다. 테스트 영수증은 결제 확인으로 표시되며, 공식 풀이 보관함은 운영 형식의 유효한 구매 권한을 조회합니다.

## 발급 서버 권한 검토안

`commerce_approved_saju_issuer_facades_v1.sql`은 발급 전용 실행 역할과 구매 범위가 고정된 함수들을 정의합니다. 발급 서버는 검증된 회원으로 현재 구매 권한과 구매 시점에 고정된 출생정보를 조회합니다. 같은 풀이에 실행 중인 요청이 있으면 추가 발급 시도를 만들지 않습니다. 완료할 때 구매 권한을 다시 확인하고 저장과 구매 연결을 한 트랜잭션에서 처리합니다.

저장 시에는 같은 발급 트랜잭션에서 현재 시도와 구매 범위를 확인하고, Saju 원문에서 Reading ID만 바뀐 결과의 해시를 대조합니다. 운영 검토에는 발급 전용 로그인, 인증된 Saju 공식 판정 검증기, 기존 운영 DB 기준과 복구 증거가 필요합니다. 이 SQL은 로그인 멤버십을 부여하지 않습니다. 적용이 승인된 경우 발급 서버에만 전용 역할을 부여하고, 중단할 때는 발급 서버를 먼저 끈 뒤 해당 로그인에서 전용 역할을 회수합니다. 구매 및 보관함 데이터는 보존합니다. 관계 비교는 두 출생정보를 쓰는 공식 발급 계약이 별도로 필요합니다.

개인 명식의 공식 발급 후보는 구매에 고정된 해석 버전과 A4 발급 시도 ID를 기존 Saju HTTPS 요청에 전달합니다. Saju의 운영 해석 구성이 완성된 판정을 반환하면 요청과 응답 해시, 해석 구성 해시, 해석 버전, 발급 시도 ID, A4 출처 ID를 Ed25519로 서명합니다. 명하는 신뢰할 공개키와 해석 구성 해시를 서버 설정에 고정해 이 값을 모두 대조합니다. 출생정보 해시는 기존 구매 범위 조회에서 가져오고 저장 시 DB가 다시 확인합니다.

이 연결을 설치하려면 Saju에 검토된 운영 해석 구성과 상품별 해석 버전, 발급 전용 서명키와 기존 A4 검증 경로를 준비해야 합니다. 명하는 공개키와 해당 운영 해석 구성의 해시를 확인한 뒤 연결합니다. 캐릭터는 저장된 공식 판정을 받아 상담 문장을 생성합니다. 발급 서버는 Saju에서 판정을 계산하는 동안 생성 모델 호출이 0건이었음을 확인해야 합니다. 정식 연동을 중단할 때는 판매와 신규 발급을 차례로 정지한 뒤 발급 전용 역할과 해당 서명키 신뢰를 회수합니다.

검증된 영수증으로 구매 권한을 발급하는 트랜잭션은 상품 구성별 작업을 기존 `outbox_events`에 함께 저장합니다. 같은 영수증을 다시 처리해도 작업은 하나입니다. 발급 워커는 전용 역할로 승인된 구성과 해석 버전에 맞는 작업을 가져와 기존 발급 서비스를 실행합니다. 보관함 저장이 끝난 뒤에만 작업을 완료합니다. 저장 직후 워커가 종료되면 다음 워커가 기존 풀이를 확인하고 작업을 닫습니다. 이미 시작한 Saju 호출의 결과가 불확실하면 기존 발급 시도에 남겨 두고 권한 있는 복구 절차를 거칩니다.

운영 연결에는 영수증 함수와 전용 작업 함수 설치, 발급 워커의 실행 주기, 상품별 Reader와 해석 버전 설정이 필요합니다. 중지할 때는 판매와 워커 실행을 멈추고 발급 역할을 회수합니다. 저장된 구매 권한과 대기 작업은 유지됩니다.

발급 서버는 검증한 Saju 서명을 풀이 저장과 같은 트랜잭션에서 보존합니다. 구매자가 후속 질문을 하면 별도 발급 연결로 해당 서명을 읽고, 저장된 풀이에서 Saju 원래 Reading ID를 복원해 서명에 담긴 원본 해시와 대조합니다. 다른 구매자나 환불한 구매자는 이 경로에 접근할 수 없습니다. 기존 보호 답변의 암호화 저장과 전송은 승인 상품 구매 연결을 인식하도록 별도 운영 검토가 필요합니다.

## 후속 답변 암호화 저장 검토안

`commerce_approved_saju_paid_answer_scope_v1.sql`과 `commerce_approved_saju_paid_answer_storage_v1.sql`은 승인 사주 발급 함수와 기존 Reader 보호 스키마가 설치된 격리 DB에서 순서대로 한 트랜잭션에 적용합니다. 구매 영수증, 현재 권한, 저장된 공식 판정의 서명과 응답 해시를 대조합니다. 저장과 환불은 같은 순서로 영수증과 권한을 잠급니다. 정확한 회원·대화·질문·발급 시도를 검증한 뒤 기존 보호 테이블에 암호문을 넣고, 일반 Chat에는 고정 완료 문구만 남깁니다. 기존 Chat의 생성 본문, AI 실행 로그, Memory와 Outbox에는 보호 답변을 기록하지 않습니다.

전용 실행 역할은 회원 확인, 암호문 저장 및 조회 함수만 실행할 수 있습니다. 일반 API, 결제와 발급 역할은 해당 함수에 접근할 수 없습니다. 이 후보는 로그인 멤버십을 부여하지 않습니다. 환불 뒤에는 암호문 조회와 동일 저장 요청의 재실행이 차단되며, 원래 권한 철회 시각으로 삭제 작업을 대기열에 기록합니다. 승인 사주 삭제 작업은 외부 삭제 원장과 키 파기 경로가 연결될 때까지 기존 워커의 처리 대상에서 제외합니다.

서버의 비공개 재열람은 기존 복호화, 키 확인, 삭제 원장 검증을 사용합니다. 회원을 다시 확인하고 승인 사주 전용 함수로 암호문을 찾습니다. 독립 삭제 원장의 유효한 읽기 권한을 확인한 상태에서만 키를 사용하고, 거래 종료 후에도 읽기 권한을 다시 확인합니다.

승인 상품 발급기는 Saju에 정본 Reader 근거를 요청합니다. 한 번의 계산에서 나온 판정·조건·근거 참조와 기존 풀이 응답을 각각 해시하여 같은 발급 시도 서명에 묶습니다. 명하는 서명과 두 해시를 검증한 뒤 해당 근거를 기존 비공개 발급 영수증에 저장합니다. 보관함 응답은 기존 형식을 사용합니다. Reader는 현재 구매 권한을 확인하고 해당 영수증을 다시 검증한 뒤 Saju의 정본 판정을 사용합니다. 오래된 발급의 보관함 조회는 기존 권한을 따릅니다. 후속 상담에는 그 풀이와 일치하는 서명된 정본 근거가 필요합니다.

운영 검토 전에는 이 후보를 격리 환경에서만 사용합니다. 공개 후속 상담에는 실제 Reader 질문의 기준 근거를 DB가 이어 주는 경로, 키와 삭제 원장, 복구 이후 재열람 제한 및 검증이 필요합니다. 장애로 중지할 때는 전송을 차단하고 전용 로그인 역할을 회수합니다. 저장된 암호문과 삭제 작업은 보존하고, 삭제·키 파기는 승인된 개인정보 절차를 따릅니다. 격리 검증은 거래 전체를 폐기할 수 있는 전용 DB에서 수행합니다.
