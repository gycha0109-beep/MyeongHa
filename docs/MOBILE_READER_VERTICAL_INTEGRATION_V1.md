# Mobile Saju / Face → Reader integration (contract-first)

Status: **Transport prepared, public Reader and Face upload blocked**.

## Architecture

- Saju preview: existing public `POST /api/me/saju/preview-reading`. The delivered/fallback Reading is generated by the Saju authority; a selected Reader does not change this evidence or its semantics.
- Official Reading: archive is read from the active subject through `readOfficialReadingRecordV1`. Reading history Reader ids are provenance, not an active selected Reader or Chat Thread authority.
- Reader interpretation: server-owned `POST /api/me/readings/reader-interpretation/preview`, requiring **only** `threadId` and `officialReadingId`. The server resolves the owner-approved single-character thread, Reader identity, Official Reading access, interpretation, Memory, and Saju provenance. No client-supplied `readerCharacterId`, `sajuDomain`, text, derived traits, or payment/entitlement assertions.
- The public Vercel rewrite / dispatcher for Reader interpretation is **not released** as of 2026-10-08. The production activation code supports `off` or limited `internal_preview`, but is not an end-user public release. Tests explicitly require the production route to be absent.
- `packages/api-client/src/reader-interpretation.ts` validates the exact server response schema and returns only a preview interpretation or protected fallback. `publicRouteActivated` defaults to **false**. Native mobile service is constructed in the disabled state. These are transport contracts, **not** release approval.
- A Reader selection in Web and a future mobile selection screen is **presentation-only** until eligible Reader and official record authority are confirmed by the server. User-entered URLs or locally selected portraits do not become Reader identity.

## Intended Saju flow (not yet public)

1. Current subject establishes Birth Profile and source-approved Saju calculation / preview.
2. Production Reading lifecycle creates a persisted Official Reading and its authorized Reading Session.
3. The server resolves eligible Reader grants, obtains a canonical Reader choice, and opens/reuses the exact Member-owned single-character thread. A browser/mobile Reader hint is insufficient.
4. With a server-approved Official Reading id **and** thread id, the client can request Reader Interpretation; the server checks access, identity, materialization, and source provenance. The client uses **only the server-returned Reader id** for presentation.
5. On `protected_fallback` no fabricated Reader text or Saju claims are rendered. Access failures are not silently substituted with ordinary Preview text.

## Face blocker

Mobile M7 and Web currently support only camera/gallery selection and local preview. Face media is **not** uploaded or analyzed. M7 explicitly notes that `expo-image-picker` `exif:false` does not prove the image bytes had EXIF metadata stripped. Before implementing ingestion, the owner must supply a reviewed server-side intake API with metadata removal, consent and retention/erasure, image size/type validation, neutral observation provider, governed Face result admission, and Official Reading → Reader authority. Do **not** send raw photos to an arbitrary `/api` endpoint or mislabel photo staging as analysis.

## Release gates / acceptance

- Public Reader activation needs explicit owning-track approval, route rewrite + dispatch + rollout policy, Reader grants, server truth-backed Open/Read contract and live canary.
- Native must not send Reader requests while `publicRouteActivated` is absent/false.
- Any response with wrong Official Reading, Reader identity, Saju domain, interpretation hash, unexpected private fields, or malformed utterance fails closed.
- Face must not transmit image data until the approved intake and retention boundary ships.
- Guest / Member subject changes require reread; Client must never merge accounts or fabricate a Reader binding.

This contract PR does **not** modify Vercel rewrites, enable any restricted endpoint, create Official Readings, send photos, or build an APK.
