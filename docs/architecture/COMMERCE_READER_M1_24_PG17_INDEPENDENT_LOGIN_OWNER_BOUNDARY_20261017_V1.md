# M1-24 — Independent PG17 TCP login, role-escalation and Owner-boundary probes

> 2026-10-17 · Watchtower-Track: commerce · stacked Draft on M1-23 #2259. All work in disposable CI PG17 only. **No live SQL, payment, private Reader issuance or release authority.**

## Gap after M1-23

M1-23 switched `current_user` under `SET LOCAL ROLE` but `session_user` was still PostgreSQL CI's stock `postgres` superuser. The SQL permission probes were meaningful, yet the privileged session connection could make the observed identity and privilege escalation guarantees differ from independently authenticated application sessions.

M1-24 opens actual **new TCP connections** with dedicated, randomly passworded, disposable non-superuser PostgreSQL `LOGIN` principals. Every principal has **only one** target runtime role membership, with `ADMIN FALSE, INHERIT FALSE, SET TRUE`. The account must authenticate with its generated password and explicitly `SET LOCAL ROLE` inside a read-only transaction; without `SET ROLE`, an API-affiliated synthetic login has no inherited minimal-read EXECUTE. All synthetic roles are local to the CI service and are dropped during cleanup.

The test verifies separate `session_user` and `current_user` values, `NOSUPERUSER` and `NOBYPASSRLS` for all six runtime roles; it is a stronger SQL session-security test than M1-23. It **does not** use an actual Supabase credential, managed migration principal, production login, network authentication policy or release approval.

## Actual SQL permission tests

- Approved API runtime identity, invoked from **independent authenticated TCP session**, executes `qry_official_reader_unknown_commit_minimal_v1(NULL::uuid,NULL::uuid)` and must reach its input guard **SQLSTATE 23514**. This is not a user-data read.
- Other five runtime roles trying that same minimal-read function must return **SQLSTATE 42501**.
- All six roles attempting private D2 receipt issuer and Reader binder must return **42501**; no Writer side effects.
- API identity attempting `SELECT * FROM` the five Receipt/Grant/Entitlement/Reader/Outbox source tables `LIMIT 0` must return **42501**.
- Every independent role must be unable to `SET ROLE postgres`, `CREATE ROLE` or transfer the minimal-read function OWNER (SQLSTATE `42501`). For `GRANT EXECUTE TO PUBLIC`, PostgreSQL may instead emit a warning and exit successfully without adding any privilege; **the test inspects the effective function ACL inside the rollbacked transaction** and fails only if PUBLIC EXECUTE actually becomes available. Privileged DDL probes are wrapped in rollback-only transactions.
- M1-18 positive catalog and rollbacked four negative permission-drift checks are repeated. The source-tree `1970` function Owner is explicitly confirmed as **CI postgres**, producing a **HOLD, not a false Owner parity PASS**.

## Fixture trust boundary

The PostgreSQL CI service starts as `POSTGRES_USER=postgres`; this bootstrap superuser creates the six **independent LOGIN** principals and one narrow `SET`-only membership for each. All behavioral probes are submitted through distinct TCP connections authenticated by those login identities, **not** an inherited superuser connection. Disposable password values are generated by `openssl rand`, not committed or printed; `umask 077` and a temporary directory protect probe output. Cleanup drops only test principals.

The shell refuses anything outside `CI=true`, `PGHOST=localhost`, `PGPORT=5432`, `PGUSER=postgres`, `PGDATABASE=myeongha_ci_case_*`, PostgreSQL 17 and requires the existing CI fixture password. Supabase production-secret environment keys must be absent. The case uses existing `apply_pg17_migrations_without_birth_authority` with the well-documented `0860` exclusion, and the shared PostgreSQL 17 DB suite (no new workflow).
