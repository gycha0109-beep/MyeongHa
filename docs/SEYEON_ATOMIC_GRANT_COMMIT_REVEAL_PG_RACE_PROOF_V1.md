## Current authority boundary (verified against main)

- Se-yeon native turn flow: server Context Assembly -> model generation -> `persistGenerated` -> `persistValidated` -> `commitTurn`. Each port call is executed under its own canonical Subject PostgreSQL transaction. The current `commitTurn` selects `public.cmd_commit_seyeon_chat_turn_runtime_v2` without a durably pinned, same-transaction personal-record grant vector.
- The deployed personal Memory/Fact Projector registry is empty; Se-yeon public chat route is still unmounted and WRITE_DARK. This is a **future activation threat**, not a demonstrated currently exposed user exploit.
- PR #1841 added a shadow-only read-again checker with `permitsPublication:false`; a read/check in a separate transaction cannot prevent a concurrent revoke between that check and DB Commit or between DB Commit and HTTP Reveal.
- Generic Official Reader A3 preflight is not Commit/Reveal authority. Its purchase-backed exact grant issue is coordinated under #1827.

## Two-session PostgreSQL evidence (not a Production migration)

The existing `reader-memory-tenant-boundary` DB CI case now invokes `test/db/seyeon_atomic_memory_grant_race_v1.sh` after the established Subject/Reader regression.

1. Fixture SQL creates an **isolated synthetic Subject, Memory, and explicit Se-yeon Grant** plus a **test-only** SECURITY DEFINER helper. The helper is executable by `myeongha_api_executor` only and checks server-pinned Subject+Memory+Grant identity; its SQL locks both `record_access_grants` and `memory_items` via `FOR SHARE OF g,m` inside a transaction. The helper is not created by a migration and is dropped at cleanup.
2. Session A uses `myeongha_api_executor` with Subject context, obtains exact row locks and holds the same transaction open across the simulated Commit window.
3. Independent session B attempts to revoke the active Grant and Memory. Each UPDATE must fail on a 600 ms PostgreSQL `lock_timeout`; any other error or update success fails CI.
4. Once A commits, a true revoke succeeds. A subsequent privileged *fresh read* rejects the original Grant. Re-granting the same Memory with a different Grant ID **does not restore the original authorization**, while the new Grant remains independently detectable.
5. Revoking the Memory also makes the replacement Grant ineligible. All fixture records and the helper are removed after test execution.

The test validates **PostgreSQL serialization mechanics and exact-Grant check semantics**, not the real Se-yeon `cmd_commit_seyeon_chat_turn_runtime_v2`, which remains unchanged. The helper is a security test fixture; **never enable it on a live database**, copy its superuser ownership, or treat it as approved Production authority.

## Required Production owner implementation (still HOLD)

Before enabling positive personal-record Projectors or Controlled Reveal:

1. Pin each *actually admitted* personal record's verified Subject/Character/recordKind/recordId/GrantId/schema/content revision in a server-owned immutable turn/attempt provenance. Do not serialize model-generated references as authority; persist an integrity hash to detect mutation. Explicitly specify the zero-record case and other sensitive Context sources.
2. Provide a least-privilege, forward-only PostgreSQL commit procedure owned and approved by DB/character-memory. **Inside the same database transaction that commits the chat turn**, revalidate every exact record+Grant, explicit status, Subject, Reader/Character, thread and official purchase Grant where applicable; hold `FOR SHARE` or stronger locks on revocable Grant and referenced content rows **until Commit completes**. Use deterministic lock order, bounded `lock_timeout`, and deadlock/rollback mapping. No separate SELECT-then-COMMIT bypass.
3. Enforce the same committed provenance at the **HTTP Controlled Reveal and `committed_replay` paths**. On revoke, disclose **zero generated bytes**, no new paid model request, no fallback exposing stale context. Set a clear visibility linearization point; streaming bytes previously delivered cannot be recalled.
4. Prove two-session races with the **real** final commit function, including revoke-first, gate-first, regrant replacement, Memory revoke, cross-Subject and failure paths, plus real HTTP reveal/replay. Ship via DB-owner-reviewed migration and adapter PR only after exact signatures, schema and policy are approved.
