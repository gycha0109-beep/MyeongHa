# 명하 전 캐릭터 GEPA 품질 최적화 아키텍처 — 2차 검수 수정본 v0.3

> 2차 검수 기준: 2026-11-11 · 상태: **기술 계약 보완 완료 / 설계 승인 전 / 공통 GEPA 미구현**  
> 대상: MyeongHa의 Character Runtime 및 오프라인 연구 파이프라인  
> 이번 문서는 **첨부 v0.2를 다시 검수하여 실행·데이터·예산 계약을 보완한 설계 문서**이다. 코드/PR 변경·유료 실험·운영 배포는 하지 않는다. 운영 모델·캐릭터 설정·DB·기존 관계/기억 상태는 모두 현행 유지한다. 기존 여울 오프라인 연구 코드가 존재하더라도, 아래 전 캐릭터 공통 엔진이 구현됐다는 의미는 아니다.

## 0. 최종 설계 결정

**공통 최적화 실행기 한 벌을 만들되, 각 캐릭터의 권한·평가 데이터·최적화 실행·결과물은 독립적으로 격리한다.**

**1차 검수 유지:** (1) GEPA와 실제 API의 예산을 따로 제한, (2) 최종 홀드아웃을 GEPA 바깥에서 별도로 실행, (3) 잠긴 프롬프트 슬롯만 구조적으로 편집, (4) 최적화 로그·교사 피드백을 비공개로 통제, (5) 전 캐릭터 공통 규칙의 개별 퇴행을 차단한다.

**2차 검수 보강:** (a) 공통 트랙의 여러 캐릭터·모델을 표현하는 실행 계약, (b) Python/Node를 통과하는 단일 호출 게이트와 충돌 안전 예산 장부, (c) 커스텀 반사 모델의 GEPA 자체 비용 추적 0달러 문제, (d) 실제 파일 접근이 분리된 봉인 평가, (e) 명시적 GEPA 신규 API·결과형 잠금, (f) 평가·반사·로그의 모든 정보 흐름 통제.

- 공통으로 고칠 것: 한국어 비문, 근거 없는 기억, 질문 회피, 원치 않는 반복, 부적절한 사생활 주장, 비용·지연 문제.
- 공통으로 고치면 안 되는 것: 인격 차이, 감정 표현 방식, 캐릭터의 결함과 판단, 관계의 고유한 행동 원리.
- 캐릭터별로 고칠 것: 해당 캐릭터가 취할 행동과 표현 방식. **Canon·세계관 사실·권한 자체를 최적화하지 않는다.**
- GEPA는 **오프라인 후보 탐색기**다. 운영 대화마다 GEPA를 실행하지 않는다. 운영에서는 선택·승인된 프롬프트 버전과 검색된 검토 대사만 이용한다. **최적화 엔진을 공유한다는 뜻은 캐릭터별 결과·승인을 공유한다는 뜻이 아니다.**
- 여울은 첫 시험 대상이며 DeepSeek를 잠정 선택했다. **전 캐릭터가 같은 모델을 사용한다고 가정하지 않는다.**

## 1. 기존 자료에서 확인한 사실과 제안의 경계

### 1.1 확인된 현재 기반

1. `packages/character-content/src/runtime-authoring-v1.ts`는 **9명**의 `characterId` (`seyeon`, `yeoul`, `seorin`, `rahyeon`, `mira`, `taegyeom`, `yunho`, `doyun`, `baekheon`)을 저작 레이어에 포함한다. 이는 전원의 서비스 활성화를 뜻하지 않는다.
2. `docs/character/CHARACTER_RUNTIME_STANDARD_V1.md`에는 **공통 평가축**(Persona Fidelity, Agency, Relationship Continuity, Memory Quality, Long-Horizon Stability, Anti-Repetition 등)과 **R16 캐릭터 전용 평가 질문**이 이미 분리되어 있다.
3. `docs/character/YEOUL_CHARACTER_BIBLE_DRAFT_V0_3.md` 및 `YEOUL_CHARACTER_RUNTIME_DRAFT_V0_1.md`는 여울의 내용 근거지만, 헤더의 권한 상태는 여전히 **DRAFT**다.
4. 현재 연구 브랜치 `feat/character-runtime-lab/yeoul-offline-quality-v1` / PR #3187에는 오프라인 정제기, 실패 피드백, 검토 대사 검색, 프롬프트 4종 조립, 승인 없는 실험 차단, 검토표 입력 검증, 104개 응답 구조 검증이 구현되어 있다. **GEPA 최적화 실행·유료 탐색·대사 품질 향상 실측은 아직 없다.** 확인 시점 PR은 GREEN이지만 `open`이고 자동 병합만 설정되어 있어, 병합됐다고 간주하지 않는다.
5. 기존 평가: 4모델 × 3조건 × 12질문 × 2회 = 288개; DeepSeek 72개. 기존 12질문은 **개발 자료**이며, 새로운 품질 개선 증명의 최종 테스트가 될 수 없다. 신규 홀드아웃 10개 상황의 4후보×2회 비교는 80개 대화 실행/104개 모델 응답 호출에 해당한다.
6. 설계 자료 `MyeongHa_Character_System_Architecture_C1_v0.1`은 LLM을 **Character Renderer**로 두고 Canon/Persona/Behavior/Relationship/Memory/Authority를 분리한다. `MyeongHa_Integration_Spine_v1.2`는 콘텐츠 버전 자동 교체 및 권한 없는 Chat 활성화를 금지한다.

### 1.2 새로운 설계 제안

다음의 `character-optimization` 연구 패키지, 공통 평가·프로필 규격, GEPA 어댑터, 전 캐릭터 회귀 검증, 결과 승격 계약은 **현재 완료된 기능이 아니다**. 승인된 아키텍처 위에 추가하는 제안이다.

## 2. 불변 영역과 최적화 허용 영역

| 계층 | 다룰 수 있는 내용 | GEPA 변경 허용 |
|---|---|---|
| Canon / Bible / 세계관 | 출생, 직업, 고정 인간관계, 캐릭터 사실 | **금지** |
| Source authority / 기억·관계 / 사주 | 실제 사용자의 확인된 사실, 읽기 권한, 관계 이벤트, 명식·해석 | **금지** |
| Runtime Behavior 원칙 | 행동 우선순위, 금지 행동, 관계 단계별 경계 | **직접 변경 금지**. 검토된 표현 규칙으로만 반영 |
| 공통 표현 규칙 | 한국어 어법, 사용자 발화에 답하기, 불필요한 중복 방지 | **허용**: 정의된 슬롯에서만 |
| 캐릭터 표현 규칙 | 개성에 맞는 반응·질문·대화 주도 방식 | **허용**: 해당 캐릭터 전용 슬롯에서만 |
| 검토된 Few-shot 예시 | 상황에 맞춘 가상의 대화 예시 | **선택만 허용**. 검토되지 않은 대사를 정답으로 승격 금지 |
| 실제 사용자 기억/관계 | 채팅 로그, 장기기억, 관계 상태 | **학습·편집 금지**. 별도 동의·보존 정책 없이는 연구 입력 금지 |

**우선순위:** 확정 Canon/권한 > 고정 Behavior/Relationship Contract > 허용 표현 규칙 > 검토 예시 > 모델 생성물. **이 우선순위는 시스템 설계 정책이지 문자열 프롬프트만으로 보장되는 보안 격리가 아니다.**

**실제 격리 방식:** GEPA에 고정 Canon 전체를 수정 대상으로 전달하지 않고 `seed_candidate`를 허용 슬롯 이름으로만 구성한다. 반환 객체의 슬롯 키 집합·타입·길이·원문 불변 해시를 검증하고, 제안된 텍스트가 상위 지시를 우회하거나 허위 사실을 주입하는지도 차단·보류한다. 기존 서버 권한 검사 및 Output Guard를 그대로 적용한다. **정적 검사만으로 의미적 우회가 100% 불가능하다고 주장하지 않으며, 사람 검토와 공격형 테스트를 병행한다.**

## 3. 핵심 구성 요소 — 공통 7개

### A. Character Optimization Profile

캐릭터별 설정 파일. 고정 소스 버전과 수정 가능 슬롯, 말투/행동 기준, 전용 평가 질문, 모델 선택, 승인 상태를 명시한다. 캐릭터별 Bible/Runtime이 `DRAFT`이면 그 상태를 그대로 표시하며, 프로필 등록만으로 확정 Canon·운영 권한으로 승격시키지 않는다. 공통 엔진은 해당 프로필만 바꿔가며 실행한다. 캐릭터의 '성격을 자동 생성하는 프로필'이 아니라 **이미 있는 소스를 읽고 사용 범위를 제한하는 계약**이다.

### B. Immutable Context Composer Adapter

현행 Context Composer의 정책 필터를 우회하지 않는다. 고정 Canon, 현재 단계, 확인된 관계·기억 사용 가능성, 사주/제품 권한, 콘텐츠 버전 등이 먼저 결정되고 **최적화된 표현 슬롯만** 추가된다. 원본 프롬프트/버전 해시를 함께 기록한다.

### C. Evaluation Corpus Manager

각 캐릭터의 자료를 `development / optimizer_validation / sealed_holdout / long_horizon`으로 구분한다. 동일 질문의 반복·유사 패러프레이즈·대화의 앞뒤 턴이 서로 다른 분할로 흩어지지 않도록 **시나리오 가족 단위 분리**한다. 대화 내 턴과 동의어·의미적 변형까지 동일 가족으로 묶고, 가족 식별·중복 검사의 버전을 고정한다.

여울의 과거 Y01~Y12는 이미 프롬프트 설계와 실패 분석에 노출된 **개발 데이터 전체**이므로 그 안에서 분할만 바꾸어 새로운 독립 검증셋을 만들지 않는다. 신규 개발/검증 가족을 별도 확보하고 H01~H10은 최종 테스트로만 유지한다. **최종 홀드아웃의 질문·답변·점수·식별자별 진단이 최적화기와 교사/심사 입력에 노출되면 봉인 실패**로 처리한다. 특히 지금 여울 H01~H10의 합성 설계 파일은 GitHub 연구 브랜치에 있으므로, 단순히 `test_set=None`으로 전달하지 않는다고 파일 접근이 차단되는 것은 아니다. 최적화 실행 컨테이너/프로세스에는 봉인 파일·원격 저장소 접근 자체를 제공하지 않고, 평가 종료 후 별도 권한을 가진 최종 시험 실행기만 읽도록 한다. 기존 공개 노출 사실을 숨기지 않고 실험 독립성 한계로 기록한다.

### D. Feedback & Metric Engine

기존 사용자 평점·메모, 자동 규칙 위반, AI 심사, 사람의 블라인드 선택을 **서로 다른 근거**로 보관한다. 미확인 자유 의견에서 추출한 키워드는 확정 라벨이 아니다. 출력은 `점수 + 실패 원인 + 개선 가능한 표현 위치 + 위반 근거`다.

사람 검토와 AI 심사 사이의 불일치를 표본으로 교정하고 심사 모델·루브릭·프롬프트 버전을 고정한다. GEPA에 되돌리는 피드백은 **최적화용 검증/개발셋의 비식별 진단**으로 제한한다. `side_info`뿐 아니라 `dataset` 객체·`objective`·`background`·프롬프트 초안·평가기의 표준 출력/에러도 반사 모델 또는 로깅 경로에 노출될 수 있는 입력으로 취급한다. 원본 사용자 메시지·대사·개인정보가 AI 심사나 반사(reflection) 모델로 그대로 복사되지 않도록 **허용 필드 목록 기반으로 구성하고**, 전송 직전에 재검증한다. 단일 합산 점수와 AI 심사의 점수만으로 채택하지 않는다.

### E. GEPA Offline Adapter

공식 **신규** `gepa.optimize_anything.optimize_anything`의 `seed_candidate`, `evaluator`, `dataset`, `valset`, `config: OptimizeAnythingConfig` 계약으로 연결한다. Python 최적화 실행기는 별도 오프라인 프로세스로 두고, 명하의 Node 평가·호출·근거 검증 모듈을 버전된 JSON 입출력으로 호출한다. **프로덕션 API에 Python/GEPA를 새로 넣지 않는다.**

- GEPA 엔진의 **여러 텍스트 구성요소 사전(`{shared_expression: text}` 또는 `{character_expression: text}`)** 형태로 허용 슬롯만 전달한다. 초기에는 공통/개별 슬롯을 동시에 최적화하지 않고 둘 중 하나만 실행한다. 후보가 반환되어도 별도 서명된 구성요소 계약에 맞춰 검증·합성한다.
- **엔진은 `engine='gepa'`로 명시**한다. 신규 `OptimizeAnythingConfig`의 `engine_config`에 해당 버전이 지원하는 `reflection` 등 GEPA 엔진 설정을 전달한다. 레거시 `GEPAConfig`를 섞으면 반환형이 달라지므로 같은 실행 코드에서 혼용하지 않는다. 현재 신규 API의 결과 계약은 `Result.best_candidate`·`best_score`·`total_evals`·`eval_log` 등이며, 핀된 버전에서 실제 타입을 테스트한다. 타 엔진(`autoresearch`·`best_of_n`·`meta_harness`), refiner·merge·custom proposer·원격 tracking은 초기 단계에서 **명시적으로 꺼두거나 허용하지 않는다**.
- 버전마다 GEPA 설정과 결과 타입이 바뀔 수 있으므로, **검증된 GEPA 버전·Python 버전·의존성 잠금파일**을 고정하고 해당 버전의 `optimize_anything` / `OptimizeAnythingConfig` / 반환값에 대한 호환성 테스트를 실행한다. 문서의 설정 예시는 구현 코드로 복사하기 전 해당 버전과 대조한다.
- **GEPA 내장 `test_set`에는 봉인 홀드아웃을 넘기지 않는다.** 공식 API는 `test_set`을 주면 최적화 후 기준·후보에 추가 평가를 할 수 있으며 이 호출은 설정된 최적화 평가 예산 밖에서 일어날 수 있다. 봉인 평가 전용 별도 실행기로 완료 후 한 번만 평가하고 그 비용까지 승인 상한에 포함한다.
- `reflection_lm`(교사/제안 모델)과 평가자(judge)는 자동 기본값을 사용하지 않고 모델·API 경로·프라이버시·예산을 명시적으로 고정한다. 공식 `ReflectionConfig`의 기본값은 특정 외부 유료 모델이므로 **반사 모델은 통합 예산 장부를 거치는 사용자 정의 callable로 명시**한다. 이때 GEPA가 일반 callable에 대해 보고하는 `total_cost`는 **0달러**일 수 있어 **GEPA 내장 비용 중단기를 실제 과금 안전장치로 취급하지 않는다**. 실제 요청은 전용 네트워크 게이트웨이의 사전예약을 통과해야 하고, 호출 결과 비용은 우리 장부가 검증한다. 미계측 기본 LiteLLM 경로가 사용되면 중단하며, 승인 전에는 실네트워크를 비활성화한 가상 평가기로만 검증한다.
- `OptimizeAnythingConfig.sandbox=True`는 일부 에이전트/서브프로세스 엔진의 격리 설정이지 **기본 GEPA 평가기 전체의 파일·네트워크 접근 차단을 보장하지 않는다**. GEPA 실행 프로세스와 평가기/브리지를 독립적인 운영체제 경계로 제한하고, 외부 연결은 승인된 단일 요청 게이트로만 나가게 한다.

GEPA의 제안이 `mutableSlots` 밖을 건드리면 실행하지 않고 거부한다. GEPA가 낸 진단은 정책 권한이 아니라 후보 생성 피드백이다. **텍스트 내 우회 지시도 검토 대상이며, 구조 검증만으로 의미·사실 적합성을 보증하지 않는다.**

### F. Experiment & Budget Controller

학생(실제 응답) / 반사·교사(프롬프트 제안) / 심사(응답 평가) / 최종 홀드아웃 호출을 **하나의 외부 비용 장부**에서 각각 계측한다. 요청 횟수(429·재시도 포함), 대화 실행 수, 실사용 토큰, 공급자 보고 비용, 지연, 공급자/반환 모델, 프롬프트 해시를 기록한다.

GEPA `max_evals`는 평가 함수 호출 제한이며 **DeepSeek 호출 수·재시도 수나 전체 비용 상한과 동치가 아니다.** GEPA `max_token_cost`는 제안자(reflection) 측의 토큰 비용 상한이지 학생·심사·최종 테스트 비용을 포함한 총상한이 아니다. 최종 테스트 비용은 별도로 예약한다.

각 외부 요청을 보내기 **전에** 승인된 총예산·모델별 입력/출력 최대 토큰 수·추론/캐시 등 가능한 추가 요금·최악 단가·재시도 여유분으로 비용과 호출 슬롯을 보수적으로 예약한다. 학생/교사/심사/최종평가·동시 요청이 **Python·Node를 넘어 동일한 원자적 장부**를 공유하며, 확보할 수 없으면 요청을 보내지 않는다. 초기 단일 호스트 구현은 파일 잠금·트랜잭션을 갖춘 **비공개 SQLite WAL 장부** 등으로 충돌 안전하게 구현할 수 있고, DB 서버를 새로 필수 도입하지 않는다. 예약 → 요청 전송 → 실제 비용 확인 → 정산을 **요청별 고유 ID**로 연결한다. 응답이 끊기거나 프로세스가 죽어 실제 과금 여부가 불명확하면 예약을 해제하지 않고 보수적으로 보류한다. 429/타임아웃 재시도도 API 시도 횟수와 예약에 포함한다. 응답 후 실제 사용량으로 차감·정산하고 미확인 사용량, 요금표 변경, 실패 응답의 청구 불확실성, 예산 여유 부족은 새 발송을 중단한다. **사후 비용 확인만으로 이미 발생한 초과 청구를 없앨 수 있다고 주장하지 않는다.**

### G. Candidate Registry & Promotion Gate

선정된 후보도 `proposed → offline_validated → owner_reviewed → heldout_passed → release_approved`를 거친다. 상태 전이는 독립된 사용자 결정 근거와 검증 증거에 연결해야 하며 **검토표 체크·JSON의 `approvalRef` 문자열·AI 판정 자체를 사용자 승인으로 취급하지 않는다.**

공통 후보는 해당 평가 범위에 속한 **각 캐릭터의 개별 품질·금지 위반 조건을 모두 만족해야** 승격 심사에 진입한다. 아직 독립 평가 자료가 없는 캐릭터로 자동 전파하지 않는다. 같은 후보가 다른 캐릭터의 고정 설정을 오염시키면 승격 금지. 실제 운영 반영은 기존 immutable Content Bundle 및 명시적 content transition 규칙을 따르고, 기존 채팅의 설정을 조용히 교체하지 않는다. 채팅 단위 기존 버전 유지와 즉시 롤백 대상을 함께 기록한다.

## 4. 공통 최적화와 캐릭터별 최적화: 두 개의 탐색 트랙

### 트랙 G — 공통 결함 줄이기

- 입력: 각 캐릭터에서 공통적으로 관측된 한국어 비문, 말 돌리기, 근거 없는 기억, 형식적 반복, 부적절한 명령형 등.
- 최적화 산출물: **캐릭터 이름·비공개 전용 사실을 포함하지 않는** 짧은 공통 표현 규칙.
- 평가: 여러 캐릭터의 대표 시나리오를 분리된 문제로 사용하고, 모두에서 개선 또는 비열화가 관측되는지 확인. **공통 트랙의 실행 명세는 단일 `characterId`가 아닌 평가 대상 캐릭터 집합·각 모델/공급자/버전·표본 비중을 보유**해야 한다. 캐릭터·문맥군의 표본 균형을 맞추고 캐릭터별 최소 품질·최대 퇴행 허용치(실험 전에 사용자와 확정)를 각각 적용한다. **전체 평균 개선만으로 한 캐릭터의 퇴행을 상쇄할 수 없다.** 부족한 캐릭터는 합성 평가부터 구축하고, 근거 없는 일반화 대상에는 포함하지 않는다.
- 다중 작업 탐색은 공통 텍스트 슬롯을 여러 캐릭터에 적용할 때만 의미가 있다. '전체 캐릭터를 하나의 인격으로 최적화'하지 않는다.
- 특히 특정 캐릭터에서 눈에 띄는 후퇴가 있으면 전체 평균 상승만으로 채택하지 않는다.

### 트랙 C — 캐릭터별 개성·행동 개선

- 입력: 해당 캐릭터 고유 Bible/Runtime, 사용자 평가(있는 경우), R16 전용 시나리오, 관계 단계별 대화.
- 최적화 산출물: **그 캐릭터의 표현 슬롯만** 변경하는 후보.
- 공통 지시문과 다른 캐릭터의 대사는 변경하지 않는다. 다른 캐릭터의 대사를 참고하더라도 해당 캐릭터에 자동 이식하지 않는다.
- 동일 캐릭터 내부에서도 `first_contact`, `familiar`, `conflict`, `trusted`, `memory_absent`, `long_horizon` 등의 구간을 따로 관찰한다. 실제 상태에 없는 관계를 생성하지 않는다.

**실행 순서:** 먼저 C(여울)로 안전하게 연결을 입증 → 2명 이상 비교 가능한 **독립 평가 가족**이 확보되면 G의 연구를 시작 → G 후보는 지원되는 모든 캐릭터에 회귀 검증 → C를 캐릭터별 순차 확대. 처음부터 아홉 명을 일괄 유료 탐색하지 않는다. 공통 규칙과 개별 규칙을 한 번에 바꾸지 않아 원인 귀속을 유지한다.

## 6. 실제 최적화 실행 흐름

1. **Freeze** — 현재 모델 ID, 실제 공급자 제한, provider 옵션, 샘플링, Canon/Runtime/관계 정책, GEPA 버전, 제안·심사 모델, 평가 루브릭·데이터 분할 및 SHA를 고정한다. OpenRouter 모델 식별자만으로 단일 하위 공급자가 고정된 것은 아니다.
2. **Preflight** — API를 호출하지 않고 입력 데이터·개발/홀드아웃 접근 분리·모델별 요금표·총예산 사전예약·승인 범위·실제 모델 옵션·검토 대사를 검증한다. 승인 없으면 네트워크를 차단한 가상 평가만 가능하다.
3. **Generate candidate** — GEPA가 허용된 단일 표현 슬롯 구성요소만 제안한다. **제안 전에 반사 모델 호출 예산을 예약**하고, 변경 불가 영역이나 예약되지 않은 원격 API에 접근하려는 후보는 평가 전에 거부한다.
4. **Compile** — 서버 측 정책과 동일한 권한·기억 조건을 통과하는 프롬프트만 생성한다.
5. **Rollout** — **모든 Python/Node 외부 호출을 한 개의 게이트웨이로 통과**시키고 비용·호출 슬롯 예약 성공 시에만 평가용 OpenRouter → 지정 모델로 동일 입력을 실행한다. 2턴은 동일 후보·동일 반복 내 이전 응답을 연결하며, 다른 후보의 응답을 이어받지 않는다. 반환 모델과 사용된 하위 공급자·파라미터를 기록한다.
6. **Evaluate** — 결정적 필수 위반 검사, 품질 지표, 선택적 독립 AI 판정, 지연·비용을 수집한다.
7. **Reflect** — 허용된 개발/검증셋에서 **비식별 최소 진단만** GEPA의 `side_info`에 전달한다. 점수 0점 또는 필수 위반 발생 시 프롬프트 생성자는 위반 범주만 받으며 사용자 원문/민감 근거를 받지 못한다. 원본 사용자 대사·사생활 정보·봉인 홀드아웃은 전송하지 않고, `side_info`와 GEPA의 자체 평가 로그·저장 파일도 비공개로 유지한다.
8. **Stop** — 호출·비용 상한, 평가 실패, 공급자 불일치, 개선 정체, 권한 위반 시 즉시 중단한다.
9. **Freeze candidate** — 최적화 종료 후 후보를 고정한다. 기존 개발셋 결과로 개선 확정 판정 금지.
10. **Final test** — 봉인된 홀드아웃은 **GEPA의 `test_set`이 아니라 최적화 프로세스에서 파일 읽기 자체가 불가능한 별도 검증 실행기에서** 후보 선택·해시 고정 후 승인된 호출 상한 내에서 한 번만 사용한다. 기준 프롬프트와 블라인드 비교하고 추가 실험을 결정하면 신규 홀드아웃 버전을 만든다.
11. **Owner decision** — 사용자 검토, 운영 영향/비용 검토, 명시적 활성화 판단. 해당 후보·출처·실험 결과 해시와 승인 범위를 묶고, 기존 대화 버전을 침범하지 않는 롤백 경로를 같이 둔다.

## 7. 평가 방식 — 캐릭터를 획일화하지 않는 핵심

### 7.1 불합격 우선 조건(Hard Gates)

- 이미 존재하지 않는 사건·기억·관계를 사실로 만들거나 소급하는 경우.
- 다른 사용자·다른 캐릭터의 비공개 정보가 섞이는 경우.
- 현재 권한이 없는 Canon·세계관·사주 의미를 생성 또는 변조하는 경우.
- 콘텐츠 버전·관계 단계·기억 권한을 우회하는 경우.
- 금지된 유료 호출, 데이터 외부 전송, 공급자 대체(fallback) 등이 발생하는 경우.

Hard Gate에 실패하면 언어 점수가 아무리 높아도 승격할 수 없다. **자동 탐지가 완벽하다고 가정하지 않는다.** 확인 불가인 경우에는 보류한다.

### 7.2 비교 품질 지표(Soft Metrics)

| 축 | 공통 검사 | 캐릭터별 판단 |
|---|---|---|
| 한국어 자연스러움 | 비문, 번역투, 어색한 반문 | 고유 말투·호흡이 살아 있는가 |
| 발화 적합성 | 사용자 요청에 답하는가 | 자기 방식으로 대응하는가 |
| 주도성·Agency | 의미 없이 질문을 떠넘기지 않는가 | 필요할 때 자기 주장·행동이 있는가 |
| 페르소나 충실도 | 모순·인격 설명의 기계적 반복 | 해당 Character의 욕구·결함·핵심 모순이 실제 선택에 드러나는가 |
| 관계 적합성 | 단계·공유사건·기억 범위 준수 | 단계별 거리·거절·고백·질투 방식이 자연스러운가 |
| 대화 연속성 | 과거 턴 연결, 사실 오염, 응답 방향 | 긴 대화에도 고유 개성이 무너지지 않는가 |
| 반복·길이 | 상투구·반문·장황함 | 캐릭터 의도에 맞는 반복은 허용되는가 |
| 효율 | 지연, 토큰, 실제 API 비용 | 개선 이득이 추가 비용을 정당화하는가 |

점수는 **버전이 고정된 명시적 루브릭**으로 산출한다. 단일 합산점수만 보지 않고 축별 변화와 분포를 모두 남긴다. AI 심사의 높은 점수만으로 승격하지 않고 사람의 블라인드 쌍대 비교 결과를 별도로 보존한다.

### 7.3 데이터 누출 방지

- GEPA 개발셋/최적화 검증셋은 **의미적 시나리오 가족 단위**로 분리한다. 같은 질문의 동의어 변형, 반복 응답, 이어지는 턴을 한쪽에만 둔다. 합성 질문 생성자가 봉인 질문을 참조하지 않도록 출처·입력 권한을 검사한다.
- 여울 Y01~Y12의 기존 288개는 고유 질문 12개를 재반복한 개발 근거이므로 모델 개선 '증명'에 재사용하지 않는다.
- 기존 H01~H10 홀드아웃은 **최종 후보 동결 후** 별도 실행기에서만 평가한다. **GEPA `test_set`, `dataset`, `valset`, 최적화기 `background`에 투입 금지.** 같은 홀드아웃에서 여러 후보를 고르거나 수정하면 봉인 효과가 깨지므로, 이후 연구에는 신규 홀드아웃 버전을 마련한다.
- 장기기억/관계/갈등 이후 회복은 한 턴 평가로 검증되지 않는다. 별도의 장기 대화 검증 묶음이 필요하다.
- 10개 시나리오·2회 반복만으로 작은 차이의 통계적 유의성을 과장하지 않는다. 한 시나리오에서 발생한 2턴과 2회 반복 응답은 **독립 표본 104개**로 취급하지 않으며, 비교 단위는 시나리오 가족·대화 흐름이다. 실험 전에 성공 기준(최소 개선폭·허용 가능한 퇴행·필수 위반 0 여부·비용 증가 허용치)을 정하고, **캐릭터·상황군별 성능과 사람 블라인드 평가**를 같이 보고한다. 작은 표본에서 결론이 불확실하면 확대 여부를 비용과 함께 다시 승인받는다.

## 8. 모델/비용/개인정보 경계

1. **OpenRouter 호환 사용:** 모델을 서버에 설치하거나 가중치를 수정하지 않는다. 기존 학생 모델을 그대로 호출한다. 단, **실험에 쓰는 정확한 모델 ID와 운영 배포의 실사용 모델 ID는 별도로 확인**한다. 여울 개발 실험 모델 ID는 `deepseek/deepseek-v4.1-flash-1017`; 운영 확인 전 동일하다고 단정하지 않는다. 공급자 라우팅이 바뀌면 같은 모델 문자열이어도 결과가 달라질 수 있으므로, 가능하면 승인된 특정 공급자 집합으로 제한하고 결과에 실사용 공급자를 남긴다.
2. **모델별 분리:** 각 캐릭터 프로필이 student model을 고정한다. 교사·심사 모델은 별도 명시적 승인 대상으로 둔다.
3. **라우팅 옵션:** OpenRouter 지원 조건에 맞는 `provider.require_parameters=true`, `provider.allow_fallbacks=false`, `provider.zdr=true`, `provider.data_collection='deny'`를 우선 적용한다. 공급자 선택의 재현성이 필요한 실험은 지원하는 공급자 목록을 `provider.only` 등으로 별도 고정한다. **`allow_fallbacks=false`만으로는 특정 하위 공급자가 고정되는 것이 아니다.** 만족하는 공급자가 없으면 요청을 실패 처리하며 정책을 몰래 완화하지 않는다.
4. **비용:** 실제 호출·재시도·교사·심사·최종 홀드아웃을 모두 통제한다. 공식 GEPA의 `max_evals`/`max_token_cost`만으로 총 OpenRouter 비용을 통제할 수 없으므로, **전 역할 공통 사전예약 예산 장부**를 별도로 강제한다. 사전 추산은 **참고**이며 상한/승인을 대체하지 않는다. 모델 단가·최대 토큰 제한이 검증되지 않으면 시작하지 않고, 호출 후 비용 응답 누락·초과·청구 불명은 새 요청 HOLD 처리한다.
5. **프라이버시:** 연구 입력은 기본적으로 합성 시나리오·적법한 개발 평가에 한정한다. 실제 사용자 메시지·장기기억·Life Fact·Relationship Event는 별도의 수집/사용 동의·보관·삭제 정책과 비공개 실행 승인 없이는 GEPA 교사/평가에 전송하지 않는다. **사용자 평가 원본 288건도 무조건 외부 교사/심사에게 제공할 수 있는 자료는 아니다.** 사람의 평가 메모와 원대사는 기계 내 비공개 처리하고, 비식별 실패 분류·합성 사례만 반사 모델 입력으로 사용한다.
6. **보안:** 프롬프트 후보·사용자 대사는 공개 CI 아티팩트, PR, GitHub 로그에 기록하지 않는다. 최적화자는 비공개 봉인 파일과 원본 사용자 평가 파일을 **파일시스템에서 열 권한이 없고**, 일반 인터넷에 직접 나갈 수 없으며 승인된 호출 게이트만 접근한다. 공개 저장소에는 코드·해시·익명 집계·합성 테스트만 포함한다. GEPA 자체의 `output_dir`·`run_dir`·평가 `side_info`·실행 로그와 원격 심사 요청도 민감한 출력 경로다. 저장소 밖 접근권한이 제한된 비공개 디렉터리를 강제하고, 원문·식별자·API 키가 로그에 유출되지 않는지를 실행 전에 검증한다.
7. **운영성:** 최적화는 **오프라인 배치**이고, 온라인 한 턴마다 GEPA/교사/심사 모델을 추가 호출하지 않는다. 운영에서 별도 검색기를 넣는 경우에는 검색 자체의 지연·비용·권한도 측정한다. 프롬프트 길이·검토 예시 주입·토큰/컨텍스트 창 영향도 회귀 검증한다.

## 10. 단계별 구현 로드맵 및 완료 증거

| 단계 | 구현 작업 | 완료 증거 및 게이트 |
|---|---|---|
| **A. 공통 규격 분리** | 여울 전용 변환·프롬프트·검토·예산 검사를 공통 계약으로 추출; 공통 트랙의 캐릭터 집합형 실행 명세 추가 | 여울 기존 288 집계·24 검토 목록·104 턴 구조가 변경 없이 동일하게 동작, 여울/세연 테스트 프로필 수용, 두 캐릭터의 서로 다른 모델 설정이 기록됨 |

| **D. 여울 파일럿 준비** | 기존 DeepSeek 72개 실패 의견 구조화, 신규 **독립 개발/검증 가족** 확보, 검토 대사 선별 | 비교할 후보·학생/반사/심사 모델·공급자·루브릭·데이터 SHA·별도 봉인시험 예산·유료 호출 상한을 사용자 승인 가능한 패키지로 정리 |
| **E. 여울 유료 파일럿** | 별도 승인 후 GEPA 탐색·OpenRouter DeepSeek 실행·최종 홀드아웃·블라인드 검토 | 승인 범위의 호출·지출 로그 + baseline 대비 평가 결과. 미개선이면 그대로 보류 |
| **F. 전 캐릭터 확장** | 준비된 캐릭터별 자료·프로필·R16 평가 질문 추가, 표본 균형을 둔 공통 규칙 다중 작업 실험 | 캐릭터별 기준선·최소 허용치·회귀 결과 및 공통 규칙을 적용했을 때 다른 캐릭터의 퇴행 여부 확인 |

**순서는 A→B→C→D→E이며, F와 G는 실제 근거가 확보된 이후에만 진입한다.** A~D의 오프라인 구현은 새로운 유료 모델 호출을 필수로 요구하지 않는다. 단, 현재 여울 트랙에 대한 기존 승인 범위 밖의 전 캐릭터 공통 플랫폼 구현은 **본 문서 승인 후** 별도 작업 트랙으로 시작한다.

## 11. 완료를 선언할 수 있는 최소 조건

- [ ] 프로필만 교체하면 여울/다른 준비된 캐릭터가 동일 공통 엔진으로 평가된다.
- [ ] GEPA가 Canon/Memory/Relationship/Saju/콘텐츠 권한을 수정할 수 없음을 실제 테스트로 입증한다.
- [ ] 공통 실행은 캐릭터별 모델/공급자/콘텐츠 해시·표본 가중치가 포함된 집합형 manifest로 재현되며, 공통 표현 규칙은 캐릭터별 회귀 평가를 통과하고 서로 다른 개성을 평균화하지 않는다.
- [ ] 캐릭터별 평가가 자연스러운 발화와 고유 행동을 **둘 다** 검증한다.
- [ ] 최적화 검증과 봉인 홀드아웃이 **실제 파일/프로세스 접근 권한으로 분리**되고, 인위적인 평가셋 반복 사용이 방지된다.
- [ ] 학생/교사/심사/봉인 시험·재시도 포함 호출·비용 상한이 **Python/Node 간 단일 네트워크 게이트와 충돌 안전 사전예약·원자적 차감**으로 강제된다. 미확인 과금 및 비정상 종료 시 예약이 임의 반환되지 않는다. GEPA의 자체 예산만 의존하지 않는다.
- [ ] GEPA의 기본 반사 모델·사용자 정의 callable의 **GEPA 비용 0 보고**·기본 저장 경로·내장 `test_set`에 의한 **무승인 과금/홀드아웃 노출 경로를 제거**한다.
- [ ] 원문 대사·기억·비공개 메모가 외부 반사 모델과 공개 로그에 유출되지 않음을 검증한다.
- [ ] 승격에는 사용자 승인, 고정 버전, 명시적 콘텐츠 전환, 롤백 경로가 있다.
- [ ] 사람의 독립 비교에서 품질 향상이 실증되지 않으면 운영을 유지한다.

현재 위 기준은 **설계상의 인수 조건**이며 충족 여부가 확인된 것이 아니다. `ROADMAP_COMPLETE` 선언 대상이 아니다.

| 홀드아웃이 Git 작업 트리에 있어 최적화기가 읽을 수 있음 | 별도 실행 환경·파일 접근 제한; 한 번 노출된 질문군의 독립성 한계 기록 |
| Python/Node가 서로 다른 비용 장부를 가짐 | 원자적 단일 장부, 요청 ID 멱등성, 비정상 종료 예약 보류 |
| legacy/new GEPA API 혼용 | 엔진·설정/결과형·Python·GEPA 버전 잠금 및 가상 호환성 시험 |

## 13. 최종 권장안

1. **처음부터 9명 전체 GEPA 유료 최적화를 돌리지 않는다.**
2. 먼저 기존 여울 도구의 **공통 평가·권한·비용 계약만 추출**한다. 이는 전 캐릭터 엔진의 토대다.
3. **여울의 DeepSeek 파일럿**에서 실제 개선 여부를 입증하고, 동시에 최소 두 번째 캐릭터의 합성 프로필로 공통성 검증을 한다.
4. **공통 슬롯은 여러 캐릭터에 대한 다중 작업 평가로**, **고유 슬롯은 캐릭터별 단독 최적화로** 운영한다.
5. 향상이 객관적으로 확인되고 사용자가 승인한 경우에만 기존 콘텐츠 버전 절차로 적용한다.

## 14. 1차 검수 보완 사항 및 구현 선행조건

### 14.1 설계상 중대 위험 조치 (이 문서에서 수정 완료)

1. **실제 총비용 한도:** `max_evals`(평가 횟수) / `max_token_cost`(GEPA 반사 모델 예산)와 실제 전체 API 지출을 구분하고 사전예약 장부를 추가했다.
2. **봉인 홀드아웃:** GEPA 내장 `test_set`이 별도 평가를 발생시킬 수 있으므로 H01~H10은 옵티마이저에 절대로 전달하지 않고 외부 최종 시험기로 분리한다.
3. **반사 모델 기본값:** GEPA가 사용하는 기본 `reflection_lm`의 무승인 외부 호출을 차단하기 위해 명시적 모델·키·예산 계약과 무네트워크 테스트를 요구한다.
4. **변경 범위의 실제 강제:** 단순한 '불변' 문구가 아니라 허용 슬롯 구조·원문 해시·권한 기반 컴파일·의미적 우회 검사를 사용한다.
5. **개인정보/연구 로그:** `side_info`, GEPA 자동 로그, run/output 디렉터리 및 모델 심사 입력을 외부 유출 경로로 간주하고 비공개 저장·익명화·삭제 정책을 요구한다.
6. **일반화 실패:** 공통 후보의 전체 평균 점수가 높아도 특정 캐릭터의 품질이 퇴행하면 채택하지 않도록 캐릭터별 게이트를 둔다.

### 14.2 구현 전에 확정해야 할 계약 (아직 미검증/미승인)

- 실제 배포 중 캐릭터별 모델 ID·공급자·샘플링·권한 및 콘텐츠 버전의 **관측된 값**을 기록한다. 예시 이름이나 DRAFT 문서를 Production authority로 쓰지 않는다.
- 사용자가 승인할 학생/반사/심사/홀드아웃의 개별·합산 호출 상한, USD 상한, 가격 근거, 중단 규칙을 확정한다.
- 최적화용 신규 개발/검증 질문 가족과 최종 봉인 홀드아웃을 검증한다. 기존 Y01~Y12는 최종 평가에 재사용하지 않는다.
- 캐릭터별 루브릭과 **승격 성공·비열화·통계적 불확실성 기준**을 실제 데이터와 사람 검토를 거쳐 사전 등록한다.
- GEPA/Python의 실제 설치 버전을 잠근 뒤, **반환 API와 설정 스키마를 네트워크 없는 테스트로 실증**한다. 공식 문서가 다른 시점의 반환 형태를 보여줄 수 있으므로 문서의 예시만으로 구현 완료를 주장하지 않는다.
- 현재 여울 리뷰 항목 30개는 아직 사용자 확정 0건이다. 이 문서는 어떤 규칙·대사도 승인하거나 운영에 적용하지 않는다.

### 14.3 검수 결론

**구조적 방향은 적합하지만, v0.1의 비용·홀드아웃·반사 모델·연구 로그·불변 영역 검증만으로는 실제 유료 실험을 안전하게 시작할 수 없었다.** v0.2에서 설계 계약을 보완했다. **기술 설계 검수 통과(조건부)**는 구현, 실험 실행, 보안 검증, 사용자 승인 또는 품질 개선을 입증한 것이 아니다. **2차 검수에서 발견된 신규 문제는 다음 장에서 별도로 정리한다.** 기존 저장소/PR은 변경하지 않았다.

### 15.2 필수 오프라인 실증 목록

1. **신규 GEPA API 호환성:** `OptimizeAnythingConfig(engine='gepa', ...)` 형태와 반환형을 정확한 설치 버전에서 확인하고, 레거시 설정 혼입 시 실패한다.
2. **모든 외부 호출의 차단:** 모델 역할별로 한도를 넘는 요청, 직접 LiteLLM 호출, 다른 Python 프로세스의 우회 요청 모두 보내지지 않아야 한다.
3. **예산 무결성:** 병렬 예약 경합·프로세스 종료·타임아웃·429·요금 미확인을 가상 요청으로 시험한다. 미확인 예약은 재시작해도 유지되어야 한다.
4. **최적화 자료 격리:** GEPA 실행 환경에서 봉인 테스트와 비공개 원본 파일의 읽기를 시도하면 파일 시스템 수준에서 실패해야 한다.
5. **후보 문구 위반:** 형식이 유효해도 허위 기억·인격 변경·권한 변경 지시가 있는 후보는 최종 승격할 수 없다.
6. **공통 트랙 재현성:** 서로 다른 모델/공급자를 쓰는 캐릭터 2개의 표본 균형·실패·비열화 결과를 개별로 확인한다.
7. **데이터·로그 프라이버시:** 사용자 원문, 288건 평가 메모, 비공개 대사, API 키가 반사 모델·표준 출력·공개 CI에 유출되지 않는지 검증한다.
8. **품질 경계:** GEPA 개발점수 상승과 사용자 블라인드 품질 향상을 별도로 보고하고, 미개선이면 기존 운영 유지.

### 15.3 검수 판정

**설계 문서 v0.3: 2차 기술 검수에서 지적한 주요 불일치를 설계상 보완한 상태.**
이는 실제 코드·라이브러리 연동·개인정보 적합성·예산 차단·대사 품질을 실측 통과했다는 뜻이 아니다.
**전 캐릭터 공통 GEPA는 여전히 미구현이고, 유료 모델 호출·PR 변경·운영 배포는 수행하지 않았다.**

실제 개발 진입 순서는 본문 A→B→C→D→E→F→G를 유지하되, **C 단계에서 비용·봉인 격리를 실제로 입증하기 전에는 E 단계에 진입하지 않는다.**
