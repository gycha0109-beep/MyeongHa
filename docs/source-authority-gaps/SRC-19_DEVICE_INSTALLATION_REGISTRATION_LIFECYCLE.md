# SRC-19 — Device Installation Registration / Re-registration Lifecycle Authority

> Status: **OPEN / BLOCKING for production `POST /api/device-installations/register`**  
> Domain: Notification / Device Installation  
> Source authority reviewed:
> - `Usecase_re_reviewed_v2(1).md`
> - `Myeongha_DB_ERD_v0.6_AUTHORITY_FIRST(2).md`
> - `Myeonghwa_Personalized_Interpretation_Architecture_v1.3_THIRD_REVIEW(1).md`

---

## 1. Gap

Source authority defines the `device_installations` row shape, uniqueness, token-at-rest constraints, and the cross-subject account-switch rule. It does **not** define the state transition contract for repeated registration of the same physical/browser installation.

A production registration endpoint inevitably needs deterministic answers for retry, app restart, push-token rotation, capability/app-version refresh, and previously revoked rows. Those answers are currently absent from source authority.

## 2. What source authority already fixes

ERD v0.6 defines:

```text
id
subject_id
platform                 # ios | android | web
installation_key         # client stable installation id
push_token_encrypted
push_token_key_id
token_fingerprint
app_version
client_capability
last_seen_at
revoked_at
created_at
```

and the following invariants:

```text
active (platform, installation_key) is globally unique
active token_fingerprint is globally unique
push_token_encrypted/key_id/token_fingerprint null-shape is coherent
logout/account switch revokes the old installation before the same install/token attaches to another subject
```

The notification source boundary also requires revoked installations to be excluded from future delivery.

The repository already has an authoritative standalone revoke command, `cmd_revoke_device_installation_v1`, which is intentionally limited to setting `revoked_at` for an active canonical owner and replaying an already-revoked result.

## 3. Missing authority

Source does not decide:

### 3.1 Same-subject registration retry

For an active row with the same `(subject_id, platform, installation_key)`, should a repeated register request:

```text
A. replay the existing row unchanged
B. update mutable observation fields in place
C. revoke the row and create a new row
D. require a caller-visible registration revision/precondition
```

### 3.2 Push-token rotation

When the same installation receives a new push token/fingerprint, source does not define whether to:

```text
A. mutate token ciphertext/fingerprint on the existing row
B. revoke old row + create a new installation row
C. keep installation identity but append separate token provenance elsewhere
```

It also does not define the atomic ordering when the new token fingerprint is currently active on another installation owned by the same subject.

### 3.3 Revoked-row re-registration

Source states that cross-subject account switch must revoke before reattachment, but does not specify whether a later registration:

```text
- reactivates the revoked row,
- creates a new row with a new id,
- or preserves a logical installation lineage through another mechanism.
```

Reactivating in place is not source-authorized merely because the table contains `revoked_at`.

### 3.4 Row identity authority

Source does not state whether `device_installations.id` is:

```text
- generated by the server per registration generation,
- generated/stabilized by the client,
- or preserved across same-installation re-registration.
```

### 3.5 Observation-field refresh

`app_version`, `client_capability`, and `last_seen_at` exist, but source does not define which registration/retry events may update them, whether updates require CAS/revision semantics, or whether `last_seen_at` is registration-only vs general heartbeat authority.

## 4. What the implementation must NOT invent

Until source authority resolves SRC-19, do not claim a production-authoritative `POST /api/device-installations/register` implementation that silently chooses any of these policies:

- UPSERT by `(platform, installation_key)`;
- revoked-row resurrection;
- token rotation by in-place UPDATE;
- revoke-and-recreate generation semantics;
- caller-supplied installation-row identity as retry authority;
- automatic stealing/rebinding of an active token fingerprint;
- automatic app-version/client-capability/last-seen mutation semantics.

Database uniqueness errors are not a substitute for a lifecycle contract.

## 5. Current safe boundary

The following remain source-complete:

- `device_installations` schema and partial uniqueness constraints;
- token ciphertext/key/fingerprint null-shape enforcement;
- owner-scoped standalone revoke;
- account deletion revoking active installations;
- delivery selection excluding revoked installations;
- cross-subject rule: old installation/token must be revoked before attachment to another subject;
- service-side raw-token encryption/fingerprinting boundary.

The following remains blocked:

```text
POST /api/device-installations/register
→ deterministic create/replay/re-register/token-rotation lifecycle
```

A narrow **first-ever insert only** could be persisted internally, but exposing it as the production register endpoint would be incomplete because network retry/re-registration semantics are part of the endpoint's normal lifecycle.

## 6. Required source resolution

Source authority should define one deterministic registration state machine covering at minimum:

```text
first registration
same request retry
same installation + unchanged token
same installation + rotated token
same token + different installation, same subject
same installation/token after logout/revoke
cross-subject account switch
app_version/client_capability refresh
last_seen_at update authority
row id / generation identity
concurrent register requests
```

It should also define the idempotency/concurrency key used to distinguish replay from a new registration generation.

## 7. Verification gate after resolution

At minimum:

- concurrent first registration produces one authoritative active installation;
- exact retry converges deterministically;
- token rotation preserves the selected source-approved lineage semantics;
- an active token cannot be attached to two installations;
- cross-subject rebind fails until old ownership is revoked;
- revoked installations never receive new deliveries;
- revoked-row resurrection occurs only if source explicitly authorizes it;
- app/capability/last-seen fields change only through the source-approved transition;
- no raw push token is stored outside the encrypted/token-fingerprint boundary.

## 8. Relationship to existing revoke authority

`cmd_revoke_device_installation_v1` remains valid and does not depend on SRC-19. SRC-19 only blocks the inverse/registration lifecycle.

```text
revoke existing owned installation = source-complete
register / re-register / rotate     = SRC-19 OPEN
```
