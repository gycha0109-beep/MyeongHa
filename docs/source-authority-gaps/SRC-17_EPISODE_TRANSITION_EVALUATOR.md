# SRC-17 — Episode Start / Advance Transition Evaluator Authority

**Status: BLOCKING BEFORE AUTHORITATIVE `POST /api/episodes/:id/start` OR `/advance`**

## Source-backed contract already fixed

Usecase v2 defines an Episode as containing:

```text
participants
entry condition
scene graph
choices
relationship events
unlock reward
version
```

ERD v0.6 additionally fixes the persistence boundary:

```text
user_episode_progress
- current progress projection per subject + episode + content bundle
- state = not_started | active | completed | abandoned
- current_node_key
- monotonic revision

episode_progress_events
- idempotent append-only ledger
- event_type = started | advanced | choice | completed | abandoned
- from_node_key / to_node_key / choice_key
- source_turn_id
- revision_before / revision_after
- UNIQUE(progress_id, event_dedupe_key)
- UNIQUE(progress_id, revision_after)
- revision_after = revision_before + 1
- source turn, when present, must use the same pinned content bundle
```

ERD section 17.7 also defines the Episode advance transaction skeleton:

```text
lock progress
→ dedupe action
→ validate node/choice in pinned bundle
→ append episode_progress_event
→ append governed world/relationship events
→ update progress revision
```

The remaining gap is therefore **not** the existence of a transaction skeleton or retry ledger. The gap is the governed evaluator contract required to decide what a valid start/advance actually is.

## Missing authority

The current source does not define enough executable semantics for an authoritative Episode transition evaluator. In particular it does not specify:

```text
1. Episode artifact / scene graph schema
   - how nodes, edges, terminal nodes, entry node, choices, conditions, and actions are represented
   - schema versioning and validation rules

2. Start semantics
   - how POST /api/episodes/:id/start chooses the exact content bundle/release pin
   - whether an existing not_started/active/completed/abandoned row may be restarted
   - initial current_node_key and started event shape
   - entry-condition evaluation order and failure behavior

3. Advance validation semantics
   - which current states permit advance
   - exact legal relation between current_node_key, choice_key, and to_node_key
   - whether the client supplies a desired transition or only a choice/action key
   - terminal-node handling and completed/abandoned transitions

4. Condition evaluator contract
   - syntax and type system for entry/edge conditions
   - supported inputs from relationship state, entitlements, unlocks, Life Facts, Saju semantic conditions, or other domains
   - missing/unknown input behavior
   - version pinning for evaluator/policy semantics

5. Choice/action semantics
   - choice_key uniqueness scope
   - disabled/hidden choices
   - consequences encoded in the bundle versus generated by a governed policy
   - deterministic ordering when multiple actions are emitted

6. Governed side-effect application
   - mapping from Episode actions to world_events, relationship_events, and character unlock changes
   - required policy/version evidence
   - exact atomic ordering relative to progress-event append and projection update
   - behavior when one governed side effect is invalid

7. Start/advance idempotency request contract
   - source of `event_dedupe_key` at the HTTP boundary
   - same dedupe key + same request replay behavior
   - same dedupe key + different payload conflict behavior
   - response replay semantics after commit

8. Content resolution dependency
   - the public start endpoint does not expose content_bundle_id
   - subject-specific rollout resolution is separately blocked by SRC-16
   - therefore start cannot silently invent or infer a bundle-selection algorithm

9. Source-turn causality
   - when source_turn_id is required versus optional
   - which episode actions may originate from chat versus direct Episode UI
   - whether source-turn causality affects allowed transition or only audit provenance
```

## Allowed implementation before resolution

The following remain source-complete and may be implemented independently:

```text
- immutable bundle-pinned Episode catalog/participant reads
- explicit bundle-pinned stored Episode Progress reads
- relational constraints that enforce same subject/bundle provenance
- append-only/dedupe/revision invariants already defined by ERD
- non-semantic persistence primitives whose contract explicitly requires a caller-provided, already-governed decision and does not claim endpoint completion
```

Any such primitive must remain clearly separated from the authoritative `start` / `advance` evaluator.

## Forbidden claims before resolution

Until source authority defines the evaluator contract, implementation must not claim authoritative completion of:

```text
POST /api/episodes/:id/start
POST /api/episodes/:id/advance
scene graph traversal
entry-condition evaluation
choice validation
terminal/completion decision
Episode-driven relationship/world/unlock side-effect derivation
```

In particular, implementation must not invent JSON keys, infer graph edges from node names, choose a first node by lexical/database order, treat arbitrary client `to_node_key` as trusted, or silently use latest/default content selection.

## Source decision required

Source authority must define a governed Episode evaluator contract covering at minimum:

```text
Episode artifact schema + schema version
start/restart state machine
entry node selection
condition expression/evaluator contract
advance/choice request contract
legal transition rules + terminal semantics
relationship/world/unlock action schema and application policy
HTTP idempotency/dedupe behavior
content release/bundle resolution handoff
source-turn causality rules
```

After that decision, the existing ERD transaction skeleton can be implemented without inventing product semantics.
