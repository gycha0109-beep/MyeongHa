# 프론트엔드 통합 — 한국어 우선 요청 UI 로케일 계약 v1 (2026-10-21)

> Track: `frontend-integration`
>
> 근거: 다국어화 로드맵 I18N-03 및 사용자 결정 **“한국어 우선”**.
> 이 문서는 새로운 도메인 권위가 아니며 UI 표시 요청의 경계만 정의합니다.

## 우선순위 (한국어 기본)

1. **명시적 UI 선택**: 사용자가 웹 언어 선택기에서 `ko-KR`, `ja-JP`, `zh-TW` 중 선택한 값은 브라우저의 기존 UI 저장 키 `myeongha.ui.locale.v1`에 보관됩니다. 이후 요청에는 해당 언어를 사용합니다. 한국어를 다시 선택하면 즉시 한국어입니다.
2. **선택이 없거나 잘못되었을 때는 무조건 `ko-KR`**: 브라우저의 `Accept-Language`가 일본어·중국어여도 자동 전환하지 않습니다.
3. **회원 프로필의 `profile.locale`은 현재 읽기 전용**: `GET /api/me`로 읽을 수 있지만 웹의 명시적 선택 및 한국어 기본값을 덮어쓰지 않습니다. 프로필 변경·DB 업데이트·게스트 승격 동작은 이번 작업에서 하지 않습니다.
4. 서버에서 `X-MyeongHa-UI-Locale` 헤더 값이 정확히 세 코드에 포함되는 경우만 수용합니다. 누락·비표준·쉼표 목록·다른 대소문자는 `ko-KR`로 정규화합니다. `Accept-Language`는 기존 호환·브라우저 힌트일 뿐 이 선택의 근거가 아닙니다.

## 구현 경계

- 웹 공통 `ui-i18n.js`의 `getUiLocaleRequestHeadersV1()`가 요청 발생 시점의 선택 언어를 반환합니다.
- 웹의 대화방 개설, 메시지 읽기·전송, 기록 조회, 내 정보 조회, Reader 장면 요청이 이를 전송합니다. 기존 `Authorization` 및 요청 ID, 본문, 세션·재시도·idempotency 동작을 유지합니다.
- Vercel 공유 `api/me.ts` 디스패처는 실제 라우트 전달 직전에 `request-ui-locale-v1.ts`로 헤더를 검증·정규화합니다. 요청을 소비하는 하위 런타임에 표준 세 값만 전달합니다.
- 이는 **요청에서 표시 선호를 수용하는 계약**이며 **일본어/번체 중국어 공식 해석이나 생성형 Reader 응답을 허가하는 기능이 아닙니다**. 현재 세연 렌더러의 한국어 존댓말 지시와 공식 Reading·관상 권한은 변경하지 않습니다.
- 언어 변경은 이후 전송되는 새 요청에만 적용합니다. 진행 중인 요청은 요청 당시 값을 유지하고, 저장된 Reading·메시지 원문 및 ID는 재작성·재번역하지 않습니다. 웹 화면의 authored UI 텍스트만 기존 UI 다국어화에 따라 다시 표시합니다.
- 모바일은 별도 UI 언어 저장·요청 경로가 있습니다. 이 PR은 웹→공유 API 요청 전달에 한정하며 모바일 API 헤더 연동 완료를 주장하지 않습니다.

## 후속 승인 전 HOLD

- 프로필 `locale` 저장/동기화 및 계정 전환 간 전파 정책은 정해지지 않았습니다. 한국어 기본을 변경하거나 회원 값으로 자동 선택하지 않습니다.
- 사주·관상 공식 `ClaimNarrativeProfile` / `FaceNarrativeProfile`의 일본어·번체 중국어 렌더링은 source-owned 용어집, semantic preservation 게이트 및 공개 승인 전 보류합니다.
- Reader 생성형 대화 언어는 화법·호칭 및 출력 guard 검수 전 보류합니다. 헤더만으로 Reader/엔진 출력을 변경하지 않습니다.
- 기존 대화 기록을 번역하거나 완료된 한국어 풀이를 외국어 정식 풀이로 표시하지 않습니다.

## 회귀 기준

- 헤더 누락·`Accept-Language` 외국어·비허용 코드 → 서버 `ko-KR`.
- 세 가지 명시적 언어 코드 → 그대로 수용.
- API canonical dispatch 이후에도 `Authorization`, URL, 메서드, 요청 본문 유지.
- 프로필과 공개/공식 결과의 의미·권한·기록 수정 없음.
